Checking Bluetooth… Band: Not connected Storage: this browser

Hume Band Reader

Reads the band’s stored history over Web Bluetooth — service fff0, 16-byte command frames — and keeps it in this browser: heart rate, SpO₂, skin temperature, sleep segments, daily totals, and 10-minute activity buckets. Open this page in Chrome on the Pixel — Web Bluetooth does not work inside another app’s webview. Visualization and analysis are deferred; this build is capture and storage.

Step 2 · Sync

Sync stored history

Each stream is requested with a START frame, paged with a CONTINUE frame every 50 frames, and read until the band’s terminator. The band returns its whole buffer every time — duplicates are dropped on the band’s own timestamp, so re-syncing never doubles data. When the sync finishes, the Bluetooth connection is released automatically so the Hume app can connect again.

    Streams marked “usually empty” are ones the band’s firmware rarely fills; they’re still requested so a sync is complete.

    Stored data — kept in this browser

    Everything you sync is saved in this browser’s storage on this device (IndexedDB), so history accumulates across visits and re-syncs instead of resetting. It lives only here — nothing is uploaded. Clearing erases the browser store permanently, so download first if you want to keep it.

    Protocol & honest labels

    The decoders are checked right here against real frames captured from a real band. A few of the band’s fields are not what their names suggest — they’re stored raw and labelled plainly, never presented as measurements they aren’t.

    Forensic label · 0x56, byte 9

    “HRV” is a device-state index, not HRV

    The byte the band calls HRV is a device-state index. No RR intervals are ever transmitted, so real heart-rate variability cannot be computed from it. It is stored raw and shown as Band State Index.

    Forensic label · 0x56, bytes 13–14

    Blood pressure is generated, not measured

    The systolic and diastolic bytes are generated inside a ±10 clamp around a derived value — the band has no cuff and measures nothing. They are stored raw and labelled as raw bytes, never as a blood-pressure reading.

    Also kept raw: the “vascular” and “stress” bytes (bytes 10 and 12) carry the same value under two names in the band’s records, so both are preserved exactly as sent.

    Wire format
    • Service 0000fff0-…, write characteristic fff6, notify characteristic fff7.
    • Commands are 16-byte frames: opcode, mode, BCD date/time, checksum in byte 15. Modes used here are only START (0x00) and CONTINUE (0x02, always with a zero date — repeating the start date restarts the stream).
    • History streams: HR 0x55, HRV record 0x56, daily totals 0x51, activity detail 0x52, sleep 0x53, temperature 0x65, SpO₂ 0x66, plus the rarely-filled 0x54 / 0x5C / 0x5E / 0x60 / 0x62.
    • Info queries: device info 0x04, battery 0x13, MAC 0x22, firmware 0x27, band clock 0x41, step goal 0x4B.
    How syncing works, and why the Hume app still gets everything

    Reading doesn’t consume anything: the band’s history sits in ring buffers until new data overwrites it. The START frame carries a date, but the band ignores it and returns its whole buffer — so this page and the Hume app each get everything, and dedupe happens here on the band’s timestamps (metric + timestamp + value for samples, date for daily totals, segment start for sleep). No erase command exists in this page’s code. When a sync ends, this page disconnects on purpose — Bluetooth allows one connection at a time.

    Troubleshooting
    • Band not in Chrome’s list: wake it, keep it close, and make sure the Hume app isn’t holding the connection.
    • A stream ending by “idle timeout” instead of “terminator” is recorded as such in the Syncs tab — the data received is still stored.
    • The Session log (Data tab) records the exact error Chrome returned if a connection fails.
