- `Yes, build ours.` (user confirmation to build custom app instead of third-party trackers)
- Build spec from owner assistant: relational model products / product_ingredients / product_fillers / ingredient_limits + editable filler blacklist seeded with maltodextrin, rice; views: daily totals dashboard, products list with add/edit, schedule view, product detail; exact seed data for 6 products (Valacyclovir, Magnesium placeholder, Benadryl, Claritin, EGCG paused, Glycine) and ceilings magnesium 500 mg/day (CRN) and EGCG 800 mg/day (EFSA) — all entered verbatim as given, no invented doses.
- Prior conversation context: filler blacklist rule (maltodextrin, rice fillers flagged; prefer clean options), tracking of why_taking / effect_wanted / other effects, timing conflicts, monthly science watch — the app covers the tracking + filler + timing parts; science watch stays in chat/cron, not in this artifact.
- `I take 3 off these at night to help with sleep` + bottle photos for Glycine/EGCG (parent conversation) — grounded the Glycine 3g and EGCG 200mg/capsule seed values already specified in the build spec.

## Tested sources
No external APIs or web sources. All data is user-owned, entered via the UI and seeded from the build spec above. No runtime fetch hosts.

Imagery not needed: this is a data-entry / calculation tool for the owner's own regimen; no real-world subjects to photograph, and bottle photos remain in chat. UI uses typography and color coding, no image slots.

## Long-term data behavior
- **Refresh policy**: No scheduled refresh. Data changes only when the owner adds/edits products in the UI (or via a future agent edit). Totals are computed server-side on every read from current products, so they are always live.
- **Growth**: Products, ingredients, and fillers grow as the owner photographs more bottles over time (long tail inventory). Ingredient totals and schedule derive from the products table, so they scale without extra tables. Limits and blacklist are small reference tables edited rarely.
- **Ordering**: Products sorted by status (on first, then paused, then off) then name. Daily totals sorted by over-ceiling first, then largest % of ceiling, then name. Schedule grouped by timing string, products alphabetical within a slot.
- **Time semantics**: Timing is a LIST of time entries per product (product_times table, added 2026-10-30 at the owner's request: 'The schedule should be grouped by the time take n so the 9pm would have to things in it and one thing would be in both the 9am and 9pm'). Each entry is a free-text label the owner controls ('9pm', '9am', 'With meat-containing meals') plus an optional conditional flag with a short condition label. The Schedule view groups by time label (clock-like labels sorted chronologically), and a product with multiple times appears under each one. Applied to existing data: Valacyclovir = 9pm (daily, unconditional) + 9am (conditional, 'double-dose days only'); Glycine = 9pm only; so the 9pm group shows Valacyclovir + Glycine and the 9am group shows Valacyclovir marked double-dose days only. products.timing is kept as a derived summary string of the times list for backward compatibility. servings_per_day is the multiplier for daily totals (Valacyclovir seeded at 1 maintenance; breakout 2/day noted in notes, owner can bump servings_per_day during a breakout). Existing rows are converted once by the idempotent `backfillProductTimes` action (only touches products with no time entries).

## Data model (relational — the point of the app)
- products: id, name, brand, type (supplement|medication), serving_desc, servings_per_day (real), timing (derived summary of product_times), status (on|off|paused), why_taking, effect_wanted, effects_watch, notes, info_url (text, added 2026-10-30 — URL to the product's info page online: manufacturer page or Amazon listing; shown in products list and product detail, editable in the product form), review_cadence (none|weekly|monthly, added 2026-10-30 at the owner's request: 'Some supplements I should review periodically as they are for treating an acute issue. Have that as an option. Maybe weekly or monthly and you group those together probably Sunday afternoon to review.'), review_note (what to check at review), last_reviewed_at (nullable timestamp; set by the Mark reviewed action), look_into / tell_christy (booleans, added 2026-11-01 at the owner's request: 'Ok, but I also want to know the ones that I want to look into soon. So figure a way to flag that and for things I want to tell Christy about. Don't let me forget to look into it' — see Follow-up flags below), seen_source (text, added 2026-11-02 — see Where I saw it below), in_stock (bool), created_at, updated_at
- Where I saw it (added 2026-11-02 at the owner's request: 'I'd also like to record where I saw the supplement. So store stuff like "The Human Upgrade: Biohacking for Longevity & Performance: The No-Brainer Solution To Stop Overeating : 1565 / Episode webpage: https://daveasprey.com/category/podcasts/ / Media file: https://dts.podtrac.com/redirect.mp3/mgln.ai/e/p394/rss.art19.com/episodes/e770b57e-55b9-4ff8-9e47-d65bca2f2068.mp3?rss_browser=BAhJIg9BbnRlbm5hUG9kBjoGRVQ%3D--bba5bdd77df5f5806138bf3e7d4615ea7f8e6a75x" that one is for calocurb'): a free-text `seen_source` field on any product, in any status — distinct from `info_url` (the product's own info page): this is provenance, where the owner first heard of it. Stored verbatim as pasted (episode title/number, webpage, media-file link, article, video…); the UI renders any URLs inside it as tappable links. Editable from the product form's "Where I saw it" textarea; shown in Products details, on Catalog cards, and on both Flagged-tab lists (so a flagged candidate carries its source into the look-into review). Seed: CaloCurb gets the owner's pasted Dave Asprey "The Human Upgrade" episode 1565 text (episode webpage https://daveasprey.com/category/podcasts/ and the episode media-file URL above, both copied byte-for-byte from his message) via the fill-only-if-empty `runSeenSourceBackfill` inside `applyDataFixups` — it only fills while `seen_source` is still empty, so text the owner edits is never overwritten.
- Follow-up flags (added 2026-11-01): two independent booleans on any product regardless of status — `look_into` ("I want to research this soon") and `tell_christy` ("mention this to Christy"). They exist because candidates mostly live in the Catalog (status off), where they'd otherwise be invisible. Surfacing / don't-forget mechanics: a dedicated **Flagged** tab groups both lists with clear-when-done actions; the tab label and the header summary always carry the live counts; flagged items also ride along in the Sunday Review tab. Flags are set/cleared from product cards (Products details + Catalog), the product form's "Follow-up flags" section, the Flagged tab itself, or the `setProductFlags` action. Seed: CaloCurb gets both flags via the fill-only-if-unset `runFlagsBackfill` inside `applyDataFixups` — the owner added it to the Catalog explicitly to look into (a new study is expected, per the creator) and to suggest to Christy for over-hunger; the backfill only applies while both flags are still unset so a flag the owner deliberately clears is never re-added.
- Periodic review semantics (added 2026-10-30): cadence is per product, default none — no existing product is auto-enrolled, the owner opts acute-issue items in from the product form. All cadences anchor to Sunday afternoon: weekly = every Sunday, monthly = the first Sunday at least 28 days after the last review. Next-due and overdue are computed client-side in the viewer's local timezone from last_reviewed_at (never-reviewed items are due for the coming Sunday). The Review tab groups everything due for the coming Sunday into one batch, then lists Weekly and Monthly groups with next dates; Mark reviewed stamps last_reviewed_at = now and reschedules. Off products are excluded from the review queue; paused products stay in it, dimmed/labelled.
- Info links (verified manufacturer links, confirmed via live page reads 2026-10-30, copied verbatim — never guess a URL; leave empty where no verified link is known): Glycine (NOW Foods 1000 mg) → https://www.nowfoods.com/products/supplements/glycine-1000-mg-veg-capsules ; EGCG (NOW Foods EGCg Green Tea Extract 400 mg) → https://www.nowfoods.com/products/supplements/egcg-green-tea-extract-400-mg-veg-capsules . Valacyclovir, Magnesium, Benadryl, Claritin intentionally left empty. Existing rows filled once by the fill-only-if-empty `runInfoUrlBackfill` inside `applyDataFixups`; fresh seeds include the two URLs directly.
- product_times: id, product_id FK cascade-by-action, time_label, conditional (bool), condition_label (nullable), sort_order — a product can be taken at several times; conditional entries carry a label like 'double-dose days only'
- Pill appearance (added 2026-10-30, owner's follow-up request): owner preps a week's pills at once and sometimes changes his mind, but prepped pills look alike (mostly white capsules) so the prep can't be undone without knowing which pill is which. Columns on products: pill_form (capsule|tablet|softgel|powder|gummy|liquid|other), pill_color, pill_size, pill_markings, pill_photo_key (owned blob via ctx.blobs, key `pill-photo/product-<id>`; only the key is stored, URLs resolved at read). Prep view groups by the same time slots as Schedule, showing each product's appearance + photo; look-alike warning when two products in one slot share form+color (differing imprints on both exempts them). Seeded appearance from the owner's bottle photos in the parent conversation: Glycine (NOW) = white capsules; Valacyclovir = white tablets; EGCG (NOW) = capsules only (color/size/markings left TBD, editable). Existing rows filled once by the same fill-only-if-empty pattern inside `applyDataFixups` (the single post-submit action, which also runs the times backfill).
- product_ingredients: id, product_id FK cascade, name, amount_per_serving (real, nullable for TBD), unit, elemental_amount (real, nullable), elemental_unit (nullable), elemental_label (e.g. 'elemental magnesium') — totals use elemental_amount when present, else amount; elemental rows also contribute a separate total under the elemental_label so 'total magnesium' and 'total glycinate' can both be answered from one magnesium glycinate product.
- product_fillers: id, product_id FK cascade, name — flagged is derived at read time against the blacklist (case-insensitive substring match), so editing the blacklist re-flags everything instantly.
- ingredient_limits: id, ingredient_name (unique, case-insensitive), ceiling_amount, unit, source_note
- filler_blacklist: id, term (unique) — seeded: maltodextrin, rice

## Totals calculation
Server action getDashboard: load status='on' products + their ingredients; for each ingredient contribution use (elemental_amount ?? amount) * servings_per_day, keyed by lowercased display name (elemental_label when elemental present, else ingredient name). Mass units normalized to mg (g×1000, mcg÷1000, mg×1) for summing and ceiling comparison; non-mass units grouped by (name, unit) separately. Each total row returns: ingredient, total amount + unit, ceiling (if any) + source, percent of ceiling, overCeiling flag, and per-product breakdown (product name, per-serving amount, servings/day, contribution) so the owner can see which products stack up.

## Rejected approaches
- **Tried**: Single flat spreadsheet-style table (one row per product, dose as text)
  **Why rejected**: Cannot represent multiple ingredients per product or sum one ingredient across products — the exact many-to-one problem the owner named.
- **Tried**: Third-party apps (StackIQ / SuppTrack / SuppCo) discussed in parent conversation
  **Why rejected**: No public API to integrate, and they lack the owner's filler blacklist, effect-wanted tracking, and regimen context. Owner explicitly chose 'build ours'.
